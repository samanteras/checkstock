# CheckStock

Небольшой прототип учёта товара на складах фулфилмента (ФФ). Стек: Python, FastAPI, PostgreSQL, HTML/CSS/JavaScript. Один магазин, без подключения маркетплейса и авторизации: приложение предназначено для локальной проверки тестового задания.

## Запуск с пустой базой

Нужен запущенный PostgreSQL и Python 3.11+. Установщик для Windows доступен на [странице PostgreSQL](https://www.postgresql.org/download/windows/). Запомните пароль пользователя `postgres`. Из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
# В .env замените YOUR_PASSWORD на ваш пароль postgres
python -m checkstock.bootstrap
python -m uvicorn checkstock.api:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000. Интерактивная документация API: http://127.0.0.1:8000/docs. `bootstrap` создаёт базы `checkstock` и `checkstock_test`, если их ещё нет, применяет миграцию и добавляет исходные данные. Повторный запуск не удваивает исходные остатки. Пароль в URL должен быть закодирован как URL, если содержит специальные символы. Файл `.env` исключён из Git; не коммитьте рабочий пароль.

Начальные данные: SKU-101 «Органайзер» — Север 10, Юг 6; SKU-102 «Контейнер» — Север 5, Юг 0; SKU-103 «Корзина» — Север 0, Юг 4.

## Правила учёта

Для пары товар–ФФ хранятся `physical` и `reserved_fbs`; доступно `physical - reserved_fbs`. Приход увеличивает физический остаток. Резерв FBS блокирует доступное количество, отмена освобождает его, отправка уменьшает физический остаток и резерв. Отправка перемещения или FBO списывает товар с ФФ и помещает его в путь. Приёмка перемещения добавляет товар получателю; приёмка FBO закрывает отправку без возврата на ФФ. Отправленный FBS показывается как товар «к клиенту»; отдельная приёмка клиентом в задании не предусмотрена.

Проверка количества выполняется на выбранном ФФ. Любое изменение остатка, статуса и журнала происходит в одной транзакции PostgreSQL. При создании операции обязательный `idempotency_key`: тот же ключ с теми же параметрами возвращает прежнюю операцию, с другими — ошибку 409. Повторная приёмка или отправка также не создаёт второе движение. Склад при «удалении» архивируется: его остаток и история остаются видимыми. Из него можно переместить доступный товар; уже начатые резервы и перемещения можно завершить.

Экран остатков читает складские остатки и агрегаты товара в пути в одной read-only транзакции `REPEATABLE READ`. Это исключает смешение состояний до и после параллельного перемещения. История выдаётся страницами по 50 записей.

## Тесты

Используйте **отдельную пустую тестовую базу** с именем, оканчивающимся на `_test`: тесты очищают в ней таблицы перед каждым сценарием и откажутся запускаться с другим именем.

```powershell
python -m unittest discover -s tests -v
```

Тесты проверяют резерв и отмену, FBS/FBO, перемещение и повторную приёмку, нехватку на выбранном ФФ, ключи идемпотентности, архивирование, два параллельных резерва, гонку архивации и согласованный снимок. Без `TEST_DATABASE_URL` интеграционный набор пропускается. Дополнительная проверка без БД: `python -m compileall -q checkstock tests` и `node --check static/app.js`.

Для автоматической проверки интерфейса в настоящем браузере запустите приложение с тестовыми данными и выполните:

```powershell
python -m pip install -r requirements-browser.txt
python -m playwright install chromium
$env:CHECKSTOCK_BASE_URL = 'http://127.0.0.1:8000'
python -m unittest discover -s tests -p 'test_browser.py' -v
```

Этот сценарий добавляет новый ФФ и оформляет приход SKU-103 через веб-форму, затем сверяет экран остатков и историю.

При отправке в GitHub workflow `.github/workflows/test.yml` автоматически выполняет интеграционные тесты с пустой PostgreSQL 16 в отдельном сервисе. Локальный браузерный сценарий запускается отдельно, так как ему нужен работающий веб-сервер.

## Структура и решения

- `checkstock/inventory.py` — складные операции и чтение данных; `api.py` — HTTP-обработчики.
- `migrations/001_initial.sql` — схема БД; `checkstock/seed.py` — повторяемые тестовые данные.
- `static/` — локальный интерфейс; `tests/` — интеграционные сценарии на PostgreSQL.

Прототип рассчитан на один магазин и локальный запуск. Для общего доступа потребуется авторизация и разграничение прав. API WB, прогнозирование и закупки относятся к отдельному большому проекту и здесь не реализованы.

## Сценарий видео на 3–5 минут

1. Покажите запуск из пустой базы по README и экран исходных остатков.
2. На SKU-102 попробуйте зарезервировать 1 шт. с Юга: появится «доступно 0», хотя на Севере есть 5.
3. На SKU-101 создайте резерв на Севере, отправьте FBS и покажите остаток, товар к клиенту и историю.
4. Переместите часть SKU-101 с Севера на Юг, примите и повторите подтверждение через API: второй раз остаток не вырастет.
5. Архивируйте Север с оставшимся товаром: он останется виден; покажите перемещение доступного остатка из архива.
6. Кратко объясните транзакции, ключи идемпотентности, тесты конкуренции и где ИИ помог, а что вы проверили сами.
